# Live playback rebuffer reserve and fragment continuity

Recorded 2026-09-28_22-26-11 +07. User reports stuttering/live-buffering alternation despite buffer changes, apparently on each segment.

Code evidence: waiting only set a flag; it did not pause the media element, so native automatic resumption could consume every newly appended fragment before the configured rebuffer reserve accumulated. Startup waited for startupMs but then sought to end minus liveTargetMs, discarding the larger startup reserve. Each successful append also announced live regardless of actual playback. Range handling always selected the last buffered range and could seek on every append across a gap. These are verified code defects; no claim that they are the sole cause of the user's observed camera stutter.

Changed shared copy-stream.js to pause on waiting, reset playback rate, and resume only once contiguous data reaches max(rebuffer,target). Startup preserves max(startup,target). Catchup/large-lag seek preserve configured reserve, using max(startup,rebuffer,target) during steady playback. Ordinary appends do not call play if already playing and do not announce live; playing event does. Range selection follows the playhead; a true gap recovery waits for reserve in the next available range. Explicit history eviction now retains30seconds and runs no more often than every5seconds, instead of removing back to3seconds on every fragment. This lowers decoder eviction churn at the cost of more client memory; it does not prove safety for arbitrarily long camera GOPs or bound network jitter.
