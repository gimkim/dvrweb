# Unattended recording risk review

User asks what other failures can silently stop recording while absent. Reviewed current MediaService supervisor/recording status and health endpoint. Automatic process-exit retry, RTSP10second timeout and verifiedMAC/UID rediscovery exist. However recording/REC derives from FFmpeg process alive plus RecordingEnabled, not fresh media bytes/finalized playable files. No independent recorder-stall watchdog, recording-integrity-backed health, disk-space notification or external alert channel is implemented. Supervisor publishes heartbeat after indexing; blocking/error paths can leave stale heartbeat. Web health merely returnsversion/statusok and does not confirm recording. Hardware power/WiFi/NAS outages remain outside this software process's ability to self-report if host is down.

Proposed priorities (NOT implemented in this review): monitor per-camera actual output progress and last finalized playable file with startup allowance; restart only affected reader if no progress~90–120seconds, bounded backoff and alert persistent failures. Independent NAS-local supervisor outside app checks heartbeat and can restart stalled app/recorder; off-host monitor detectsNAS/AP outage. Storage low/full/permission alerts; periodicNAS-local consistent SQLite backups and offline integrity validation. Distinguish expectedmaintenance/disabled cameras and suppress repetitive alerts. Existing recordings history should report gaps. Avoid equating processalive/HTTP200 with continuous footage or prematurely claiming captured freezes are codec related.

No source/config/deployment changes, recurring automation or external messages. No liveSQLite access or browser tests. Worklog only.
