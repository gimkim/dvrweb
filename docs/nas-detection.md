# Recording detection (1.8.0)

Completed catalogued MP4 files are analysed in the background, one at a time across all cameras. This reuses video already recorded by the single camera reader. It creates no additional RTSP connections and does not re-encode or alter recordings/live streams. Results arrive after the minute/file is finalized plus queue time, not live.

Motion uses blurred160x96 grayscale background comparison sampled at2fps with connected-area and two-frame persistence checks. Uniform exposure changes are compensated; large scene changes reset the background for3 samples. This heuristic suppresses many PTZ/IR transitions but is not a guarantee against false alarms from small pans, weather or shadows. No camera control is issued by detection.

Person detection uses Intel Open Model Zoo person-detection-retail-0013 FP16 (544x320 BGR). OpenVINO GPU is attempted first, with CPU limited to one inference thread as fallback. Sample at1fps during motion/recent person candidates, otherwise every5 seconds; two consecutive model scores>=0.60 confirm a person. Occasional idle scans catch stationary people. At low sample rates, brief/small/occluded people may be missed. A negative means not detected in sampled images, not proof that nobody appeared.

FFmpeg tries D3D11VA hardware decode; a failed initialization/no frames falls back to one-thread software decode. Decode is capped at4x recording time, one process per active clip, below-normal priority. One persistent Python/OpenVINO process keeps the model loaded. Newest clips have priority; every fourth scheduling turn takes the oldest pending clip. Existing catalogue is backfilled gradually. Queue stays in SQLite rather than unbounded RAM. Decoder errors, insufficient frame coverage, missing model/runtime and interrupted processes must never produce a negative flag. Partial/error jobs retry up to3 attempts with5-minute cooldown. Missing runtime leaves clips pending.

SQLite `detections` stores recordingId, state, serialized independent nullable motion/human results, sampled frame/inference counts, maximum score, actual inference device/decoder, version, error code, attempts and update time. States: pending, processing, complete, partial, error. Positive evidence may survive incomplete coverage; negatives need a complete sampled clip and an available detector. A completed person-negative needs at least2 inference samples. The record is deleted with retention's recording row; results cannot be saved for a removed row. A shared disk lock protects against overlapping IIS/worker owners and crash recovery resets processing rows to pending.

Authenticated recordings APIs include `detection`; neither paths nor camera credentials are added to responses. Shared web/Android UI shows SVG activity/person icons: green check=detected, grey dash=not detected in samples, amber question mark=pending/unavailable/incomplete. Accessible titles distinguish pending, processing, partial and failed. Search results use compact rows and show a legend. Search again to load updated background results. No APK update is required for installed1.0.1.

## Runtime and deployment

Run deployment/Prepare-DetectionRuntime.ps1 on the development machine, then copy its output (excluding installer ZIP and caches) outside web root to `C:\Users\tatsa\web-data\GimDvrDetection`. Includes Python3.11.9 embedded, OpenVINO2025.4.1, NumPy2.2.6, OpenCV headless4.12.0.88 and model/license. Do not put the runtime or model in public Git. Keep included license notices. Dependencies are isolated from system Python. Runtime reads no camera credentials and has no listening network port.

Optional Dvr config: `DetectionEnabled:false` disables analysis; `DetectionRuntime` changes the external directory; `DetectionDevice` defaults to GPU. No existing production config needs changing for the default path. Web owner registers the service; external-media web skips it and the independent recorder registers it instead. Published Detection/detect.py must accompany both binaries.

Validation is code-only. Synthetic motion/scene/person-score fixtures test the algorithm decisions, real local GPU/OpenVINO blank-clip fixture tests process-to-SQLite integration, and JS fixtures test icons/playback. These do not establish person recall, long-run performance, NAS GPU driver/IIS access, or real mobile layout. No private footage or production UI was used for testing.
