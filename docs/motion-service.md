# Remote MotionService (1.9.0)

NAS owns scheduling, SQLite and original recordings. It polls the configured authenticated remote `/health` every15seconds (3second timeout). Ready protocol1 enables remote work on subsequent clips; ongoing local analysis finishes normally. Each job uploads one completed MP4 over HTTPS, never a camera URL or filesystem path. On connection/HTTP/timeout/invalid/incomplete-result failure, the same queue attempt falls back to the NAS OpenVINO detector. A later successful poll restores remote routing. Cancellation during shutdown never starts a fallback job. The local Python process starts lazily and remains reusable after a fallback. One global NAS owner/clip at a time is unchanged.

MotionService is an independent .NET10 IIS application deployed to `C:\Users\tatsa\web\MotionService`, exposed at `https://192.168.1.30/MotionService`. No static files, credentials or footage are served. All endpoints require the shared bearer key. One admitted upload/analysis at a time; excess work returns429 instead of accumulating an unbounded queue. Limits:256MiB body,180seconds declared video,110seconds request deadline; NAS remote deadline120seconds. The upload is streamed to a generated temporary file outside web root, deleted in finally; crash leftovers older than1hour are cleaned on startup. No remote filename/path/URL is accepted. Persistent detector plus Windows job ownership kills Python/FFmpeg children when the host ends.

## CUDA and CPU

Remote person detection uses the official YOLOX-tiny ONNX model (COCO person class0), BGR CHW416x416 letterbox input, objectness*person score, two consecutive scores>=0.60. Motion algorithm,2fps frame sampling,1fps active/5second idle inference are shared with NAS. ONNX Runtime1.23.2 tries CUDA, including a warm inference; startup or inference failure retries CPU. CPU inference uses2threads. Remote FFmpeg tries CUDA decoding, then single-thread software decode if no frames are produced. No artificial4x read pacing on remote; NAS fallback retains its4x cap. `Motion:Device=CPU` and `Motion:Decoder=cpu` can force all-CPU operation for diagnostics.

Remote results carry `remote-yolox-tiny-v1`; NAS results retain `nas-person-v1` (Intel person-detection-retail-0013). These are different models and scores/accuracy need not agree. Existing detections are not overwritten or reclassified. Device/decoder/version remain in SQLite and logs. Sampling/negative labels retain the previous limitations; human accuracy has not been validated against private footage.

Primary model/runtime references: [YOLOX ONNX model and input contract](https://github.com/Megvii-BaseDetection/YOLOX/tree/main/demo/ONNXRuntime), [ONNX Runtime CUDA loading and compatibility](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html). Model SHA256: `427CC366D34E27FF7A03E2899B5E3671425C262EA2291F88BB942BC1CC70B0F7`.

## Private configuration and setup

Outside Git/web root, `C:\Users\tatsa\web-data\MotionService\service.json` contains `Motion:ApiKey` (random256bit), `Motion:DataRoot`, optional `Motion:RuntimeRoot`, `Motion:Device`, `Motion:Decoder`, and optional `Motion:CudaDllDirectory`. Runtime defaults to DataRoot/runtime. Prepare with `deployment/Prepare-MotionRuntime.ps1`; optional CudaBin/CudnnBin reuse installed CUDA12/cuDNN9 DLLs in an isolated runtime/cuda directory. Keep vendor licenses. Default setup downloads CUDA dependencies into the isolated Python runtime. No system Python modifications.

Publish MotionService, then run `deployment/Install-MotionService.ps1` elevated. It backs up IIS configuration, uses the existing HTTPS IP binding (does not replace other sites/bindings), configures a dedicated always-running pool, limits its filesystem grants to this service, and writes nonsecret installation status/certificate digest to DataRoot/installation.json. IIS configuration needs Windows administrator approval. Automatic IIS preload is supplemented by NAS health polls, so the first authenticated request starts/wakes the app.

NAS external data file `detection-remote.json` contains a Dvr object with DetectionRemoteUrl, DetectionRemoteKey and DetectionRemoteCertificateSha256. Web/recorder load it on startup. Use HTTPS only; redirects are disabled. An optional exact SHA256 certificate pin must match an unexpired certificate, including when the system would otherwise trust a different certificate. Without a pin normal TLS verification applies. The deployed IP endpoint presents the machine's gimgim.ddns.net certificate, verified against its local machine certificate store before provisioning. On certificate renewal update the pin on NAS and restart the owner; until then it safely falls back locally. Never log/commit the bearer key or private config.

NAS logs add remote_status, remote_complete and remote_fallback to existing detection JSONL. MotionService logs engine readiness/device, process lifecycle, job result and total elapsed time under DataRoot/logs, with the same bounded rotation. No upload bytes, paths or secrets in diagnostic entries.

## Code-only validation

`tests/GimDvr.RemoteChecks`: injected HTTP handlers exercise readiness, upload, failure, recovery, cancellation, incomplete output and TLS pinning. `tests/motion-service-integration.py <runtime>` launches separate loopback fixtures with synthetic footage, actual CUDA and forced CPU/software decoding, authentication/type/size/duration guards, invalid clip handling and temporary-file cleanup. Neither contacts the production service/cameras. NAS local fallback pipeline is covered by existing DetectionChecks. Performance from synthetic blank video is not a real-camera capacity benchmark.
